# Story 2.1: Regenerate Schedule Functionality

## Status
Done

## Story

**As a** coach,
**I want** to regenerate a new fair schedule without re-entering data,
**so that** I can explore different student pairings while maintaining fairness.

## Acceptance Criteria

1. "Regenerate" button appears after initial schedule generation
2. Clicking "Regenerate" re-runs algorithm with same inputs (names, rounds, teams)
3. New schedule uses different randomization seed, producing different pairings
4. New schedule maintains all fairness guarantees (variance ≤ 1, no conflicts)
5. Regeneration completes in < 1 second
6. Button is visually distinct from "Generate" (different color or style)
7. Multiple regenerations produce varied results (not cycling through fixed set)

### Coding Standards

[Source: docs/architecture/coding-standards.md]

**CRITICAL RULES for this story:**
- Use Alpine.js directives (`x-show`, `@click`) - NEVER use vanilla DOM APIs
- Validate before regeneration: Call `validateInputs()` in `regenerateSchedule()` method
- Reuse existing methods: Call `runGreedyFillAlgorithm()` and `validateFinalSchedule()`
- Do NOT re-parse students: Reset counters on existing `students` array
- Use Tailwind CSS utilities for button styling - no custom CSS
- Maintain single-file architecture: All code stays in index.html

**Method Implementation Pattern:**
```javascript
regenerateSchedule() {
  // 1. Validate current inputs (coach may have changed them)
  if (!this.validateInputs()) {
    return;
  }

  // 2. Reset student opportunity counters
  this.students.forEach(student => {
    student.driverCount = 0;
    student.loaderCount = 0;
  });

  // 3. Clear previous schedule
  this.rounds = [];

  // 4. Run algorithm (leverages existing Math.random() for variation)
  this.runGreedyFillAlgorithm();

  // 5. Validate final schedule
  this.validateFinalSchedule();

  // 6. Keep isGenerated = true (schedule remains visible)
}
```

**Naming Conventions:**
- Method name: `regenerateSchedule()` (camelCase)
- Button ID: `regenerate-button` (kebab-case) if needed
- CSS classes: Tailwind utilities only (`bg-green-600`, `hover:bg-green-700`)

**Button Styling Differentiation:**
- Generate button: `bg-blue-600 hover:bg-blue-700` (blue primary color)
- Regenerate button: `bg-green-600 hover:bg-green-700` (green to indicate variation)
- Both use same size: `py-3 px-6 rounded-lg` for consistency

### Randomization Approach

[Source: docs/architecture/frontend-architecture.md, docs/prd.md#FR6]

**How Varied Results Are Achieved:**
- `Math.random()` is used for tiebreaking in `selectStudentForRole()` (index.html:343)
- When multiple students have equal opportunities, algorithm randomly selects one
- No explicit "randomization seed" - JavaScript's `Math.random()` is sufficient for MVP
- Each regeneration produces statistically different results due to random tiebreaking
- No need to implement custom seeding or forcing different results

**IMPORTANT:**
- Do NOT add complexity like seeding or shuffle algorithms
- Existing `Math.random()` tiebreaking provides sufficient variation
- Multiple regenerations will naturally produce different pairings
- Focus on correct counter reset and algorithm re-invocation

### Performance Considerations

[Source: docs/prd.md#NFR1]
- Target: < 1 second for regeneration (same as initial generation)
- Optimization: Reuse existing `students` array (don't re-parse textarea)
- Optimization: Direct counter reset via `forEach` loop (simple, fast)
- Expected complexity: O(n*r) same as initial generation
- For typical sizes (30 students, 15 rounds), regeneration is instant
